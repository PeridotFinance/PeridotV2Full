# Region-block screen (Cloudflare)

Users blocked by the geo rule used to land on Cloudflare's stock "Sorry, you have
been blocked" page: unbranded, and it never says *why*. This replaces it with a
Peridot-branded screen that names the reason (regional restriction), says the
block isn't personal, and points at the single most common false positive — a VPN
exiting in another country.

## The 2 KB constraint

A WAF custom response body is capped at **2 KB**, and the feature requires a
**Pro plan or above**. That cap drives the whole design: 2 KB has no room for the
owl mascot (3.5 KB of SVG path data on its own), a background gradient, or any
scripting.

Hence two sources:

| File | Budget | For |
| --- | --- | --- |
| `public/region-blocked.waf.html` | ≤ 2 KB | The WAF custom response. **This is the one that ships.** |
| `public/region-blocked.html` | none | Fuller version (mascot, detected-region readout) for the case where the page is hosted somewhere instead of pasted. |

Build both, with the budget enforced:

```bash
node scripts/build-region-block-page.mjs
# region-blocked.waf.min.html  2023/2048 bytes
# region-blocked.min.html      9692 bytes, no cap
```

The script exits non-zero if the compact variant goes over. Edit the `.html`
sources, never the generated `.min.html`.

Both pages are fully self-contained — inline CSS, no external requests. They have
to be: the browser showing them never reaches our origin, so any `<img src>`,
font, or stylesheet reference would render as a broken box.

Do **not** try to buy space by rounding SVG path coordinates. In SVG path data a
decimal point doubles as a number separator (`1.05.5` is two numbers), so dropping
a trailing `.0` silently merges neighbouring coordinates and the owl collapses
into a featureless blob. This was tried; it looked fine in the diff and broken on
screen.

## Which route applies

On the **Free plan a WAF block response cannot be branded at all.** Custom Errors
are Pro-and-above too, and they don't cover WAF blocks in any case — they only
override origin errors. So the route depends on the plan:

- **Pro or above** → paste the 2 KB page into the rule (route A).
- **Free** → replace the block with a redirect to a hosted page (route B). This is
  the route currently chosen.

Quick plan check: open the geo rule in the WAF editor. If **"With a custom
response"** appears under the Block action, you're on Pro or above.

## Route A — WAF custom response (Pro+)

1. Cloudflare dashboard → `peridot.finance` zone → **Security → WAF → Custom rules**.
2. Open the existing geo/region rule.
3. Action **Block** → tick **"With a custom response"**.
4. Response type `text/html`, response code `403`.
   `451 Unavailable For Legal Reasons` is the semantically correct code for a
   restriction of this kind — use it if the dashboard offers it here.
5. Paste all of `public/region-blocked.waf.min.html` into the body.
6. Save, then verify (below).

## Route B — redirect to a hosted page (Free)

The page gets hosted on Cloudflare Pages (free, and a different zone, so the geo
rule can't block it), and the geo rule redirects there instead of blocking.

**1. Deploy the page.** `cloudflare/region-blocked-site/` is generated by the build
script and contains nothing but `index.html`:

```bash
node scripts/build-region-block-page.mjs
npx wrangler pages deploy cloudflare/region-blocked-site --project-name=peridot-region-blocked
```

That yields `https://peridot-region-blocked.pages.dev`. Re-run both commands after
editing the page — Pages does not pick up changes on its own.

**2. Add the redirect rule.** Dashboard → **Rules → Redirect Rules → Create rule**.
Use the *same* geo expression as the existing block rule, e.g.:

```
(ip.src.country in {"XX" "YY"})
```

Action: dynamic/static redirect → `https://peridot-region-blocked.pages.dev`,
status **302** (not 301 — a permanent redirect gets cached by the browser and will
keep firing after the user turns their VPN off, or after the country list changes).

**3. Disable the old WAF block rule.** Otherwise it may terminate the request
before the redirect is ever evaluated, and users keep seeing the stock page.

### If you later put it on `blocked.peridot.finance`

A `pages.dev` URL in the address bar looks off for a finance product, so the Pages
project can take a custom domain. That subdomain lives in the `peridot.finance`
zone, which the redirect rule also covers — so it would redirect to itself,
forever. Exclude it explicitly:

```
(ip.src.country in {"XX" "YY"}) and http.host ne "blocked.peridot.finance"
```

### What this route costs you

The block becomes a 302, so the URL changes and the response is no longer a
refusal on the original address. Machine clients following redirects land on an
HTML page. Access is still effectively denied — the origin never serves the
request — but it is a redirect, not a block, and it is worth being deliberate
about that if the restriction is compliance-driven.

## Verifying it works

Rendering is already verified locally — serve the directory and open it:

```bash
python3 -m http.server 8896 --directory cloudflare/region-blocked-site
```

What that does *not* prove is that Cloudflare actually serves it. To check that
without travelling, temporarily give the rule a second trigger you can hit from
anywhere. Append to the rule expression:

```
or (http.request.headers["x-peridot-blocktest"][0] == "1")
```

Then, from any machine:

```bash
curl -sSD- -o /tmp/blocked.html -H "x-peridot-blocktest: 1" https://peridot.finance/
```

- **Route A** — expect `HTTP/2 403` and our markup in `/tmp/blocked.html`, not
  Cloudflare's stock page.
- **Route B** — expect `HTTP/2 302` and a `location:` header pointing at the Pages
  URL. Add `-L` to follow it and confirm the page itself comes back.

**Remove the test clause afterwards.** It only ever triggers the restriction, so a
leaked header name can't grant access, but it has no business staying in the rule.

Then confirm once from a real blocked region (VPN exit node) that the page appears
and that the geo condition itself still matches as intended.

### Worth checking while you're in there

The rule applies to every request from a blocked country, including
machine-to-machine ones. If any Bridge webhook, Stellar RPC callback, or partner
integration calls us from an IP in a restricted country, it now receives an HTML
page where it expects JSON. This was already true with the stock block page, so it
isn't a regression — but the rule is worth an `and not starts_with(http.request.uri.path, "/api/")`
exclusion if anything like that exists.

## Googlebot is one of those machines

**Search Console, 2026-08-20: 14 pages "Blocked due to access forbidden (403)",
first detected 25/07/2026 and still climbing.** Every one of them is under
`/app/` — `/app/dashboard`, `/app/leaderboard`, `/app/markets/{peridot,bnb,aster,gmon,…}` —
while the marketing pages on the same host index normally. A rule that blocked
the whole site would not produce that shape; a geo rule scoped to the product
surface produces exactly it. `/app` and `/app/markets/*` were between them
earning ~50 clicks and 2,400 impressions a year, and they are now dropping out
of the index one crawl at a time.

Googlebot crawls from a published set of IPs that no `ip.src.country` expression
is aware of, so from the rule's point of view it is simply traffic from wherever
Google routed it that day. Confirm before changing anything — dashboard →
**Security → WAF → Custom rules**, open the geo rule, and check whether its
expression is scoped to `/app`:

```
# add to the geo rule so verified crawlers are never geo-blocked
and not cf.client.bot
```

`cf.client.bot` is true only for crawlers Cloudflare has verified by reverse DNS,
so this is not the same as trusting a `User-Agent` string — a scraper claiming to
be Googlebot still gets blocked. Note that curling the URLs from an unblocked
country returns `200`, so the origin looks healthy from a developer machine; the
only reliable read is the Search Console report or the Cloudflare firewall event
log filtered to Googlebot.

The alternative — deciding `/app/*` should not be in the index at all, since it
needs a wallet to be useful — is defensible, but then it should be an explicit
`noindex`, not a 403. A 403 tells Google the page exists and is being withheld,
which is the one answer that costs the ranking without saving the crawl.

## Automating it with an API token

Custom rules live behind the Rulesets API — the `http_request_firewall_custom`
phase entry point at `/zones/$ZONE_ID/rulesets/$RULESET_ID/rules`. A scoped token
that can push the page needs:

- **Zone → Firewall Services → Edit** (in some UI versions surfaced as *Zone WAF → Write*) — reads and updates the custom rules.
- **Zone → Zone → Read** — resolves the zone ID from the zone name.

Scope it to the `peridot.finance` zone only. Both permissions are enough to
rewrite any WAF rule on that zone, so it is not a read-only credential — treat it
like a deploy key, and prefer deleting it after use over parking it in `.env`.
